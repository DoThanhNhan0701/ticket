# PROMPT: FULL FRONTEND END-TO-END TESTING & USER EXPERIENCE VALIDATION

## 1. Objective

Act as a Senior Frontend QA Automation Engineer.

Your task is to analyze, explore, implement, and execute comprehensive automated Frontend testing using Playwright with Chromium.

Test the entire website from a real user's perspective.

Scope: FRONTEND ONLY.

Primary objectives:
- Test every accessible page, module, component, and interactive feature.
- Validate UI behavior and frontend functionality.
- Simulate realistic, continuous user journeys.
- Maintain a consistent browser session.
- Prevent unnecessary page reloads during internal navigation.
- Verify SPA navigation behavior.
- Test responsive layouts and user experience.
- Detect JavaScript runtime errors and UI failures.
- Generate comprehensive test coverage and execution reports.

Do not modify or test backend business logic, database structures, or API implementations.
Backend responses may be observed only to understand and verify frontend behavior.

## 3. Browser and Session Management

Use Playwright with Chromium.
Critical requirement: Simulate a continuous real-user browsing session.

Browser behavior:
- Launch one browser for the testing workflow.
- Reuse the same browser context for sequential tests belonging to the same user session.
- Reuse the same authenticated page whenever appropriate.
- Preserve cookies, localStorage, and sessionStorage during the active session.
- Do not create a fresh browser context for every test.
- Do not log in again when navigating between modules.
- Do not reset browser state unnecessarily.
- Do not manually overwrite authentication tokens.
- Avoid unnecessary browser restarts.
- Use separate isolated contexts only when required for independent tests, such as authentication isolation or parallel execution.

Navigation rules:
- Navigate using the actual website UI.
- Click sidebar menu items, header links, tabs, and buttons.
- Use the application's client-side routing.
- Avoid page.goto() for internal navigation when UI navigation is available.
- Never use page.reload() as a workaround for broken application state.
- Preserve login state when switching modules.
- Maintain browser history and navigation state.
- Allow full document reloads only when explicitly required by a feature or test scenario.

Switching accounts:
1. Finish testing with the current account.
2. Click the application's Logout button.
3. Verify that the logged-out UI is displayed.
4. Verify previously protected screens are no longer accessible through normal UI navigation.
5. Log in using the next test account.
6. Verify the new account's interface and permissions.
7. Ensure the UI does not display stale information from the previous account.

Do not manually replace tokens or browser storage to simulate account switching.

## 5. Complete Frontend Functional Testing

For every discovered frontend module, test all relevant UI interactions.

5.1 Navigation:
- Sidebar expand/collapse; nested menu navigation; active menu highlighting.
- Header navigation; breadcrumb links; tab navigation.
- Back/Forward navigation; direct-route access; unknown routes and 404 UI.
- Redirect behavior; navigation from buttons and cards; preservation of applicable UI state.

5.2 Forms:
- Input typing; required-field validation; invalid formats; min/max lengths.
- Special characters and Unicode input.
- Select/multi-select; date/time pickers; checkbox/radio.
- Reset/cancel; submission; loading; success/error notifications.
- Duplicate submission prevention; preserved inputs on validation failure.

5.3 CRUD UI:
- Open the relevant Create, Read, Update, or Delete interface.
- Enter/select test data and submit through the UI.
- Verify visible success/error feedback and resulting displayed information.
- Verify modal/drawer state and table/detail updates without unnecessary full reload.
- Use disposable records; do not destructively modify real production data.

Ticket-detail lifecycle coverage:
- Use disposable requests to exercise approval, receipt, assignment add/remove/change, forwarding, completion, closing, reprocessing and cancellation.
- Validate required reasons/recipients, cancel dialogs, processing-section save/cancel and detail attachments.
- Switch creator/handler accounts using Logout/Login UI only; handlers find assigned tickets through their task list.
- Missing actions for the real account/status are BLOCKED, not PASS.

Recruitment coverage and data prerequisites:
- Use a permitted TEST account with full recruitment permissions supplied through secure environment/stdin; never store credentials in source.
- Create recruitment seed data from the UI: Tạo yêu cầu → Bộ phận xử lý HR → Loại yêu cầu Yêu cầu tuyển dụng.

- Reopen saved forms to verify displayed values match newly saved data. Observe responses to diagnose stale UI, without replacing UI actions with API calls.
- Delete only owned candidates/interviews and retain evidence if cleanup fails. Do not modify the shared HR configuration/template or existing business records.

5.4 Data Tables:
- Search; filters; combined filters; sort ascending/descending.
- Pagination; page size; row selection; select all; bulk actions.
- Row action menus; column visibility if available.
- Empty/loading/no-results states; reset filters; responsiveness.

5.5 Modals and Drawers:
- Open; close; cancel; confirm; Escape; outside click if supported.
- Inner scrolling; form validation; nested dialogs if present.
- Background scroll; focus management; keyboard navigation.

5.6 File UI:
- File picker; drag-and-drop if available; multiple-file selection.

5.7 Feedback and Notifications:
- Toasts; alert banners; loading indicators; error/success messages.

- Test frontend presentation, not backend notification delivery infrastructure.

## 6. Real User Interaction Simulation

Example continuous journey:
1. Open the website and log in.
2. Open Dashboard and navigate via Sidebar.
3. Search and filter records.
4. Open details and the Edit form.
5. Modify disposable test data and save.
6. Verify displayed results and return to listing.
7. Open another module and continue without resetting the session.
8. Log out when finished.

Prefer Playwright locators getByRole(), getByLabel(), getByPlaceholder(), getByTestId().
Use CSS selectors only when semantic locators are unavailable.
Avoid selectors based on dynamic classes/DOM position.
Do not use fixed waitForTimeout() unless justified.
Use auto-waiting and assertions on actual UI state.
Do not replace UI interactions with direct API requests.

## 7. SPA Navigation and Page Reload Detection

HIGH PRIORITY: The website currently experiences unwanted reloads during navigation.

Check all internal navigation paths: sidebar, header, nested menus, breadcrumbs, detail links, back buttons, tabs, submission redirects, pagination, browser Back/Forward.

Detect:
- Unexpected full document reloads or hard navigation.
- Lost frontend/authentication state.
- Repeated layout initialization or unnecessary remounting.
- Duplicate frontend requests.
- Unexpected scroll resets or layout flicker.
- Broken navigation history.

Track browser navigation events and document identity to distinguish SPA navigation, full document navigation, and expected reloads.

Investigate when applicable:
- Native anchors used for internal navigation.
- window.location.href/assign()/replace().
- Incorrect router usage.
- Form submission causing browser navigation.
- Incorrect redirects, remounts, or layout configuration.
- Next.js next/link and next/navigation.
- React Router Link, NavLink, and useNavigate.

Do not modify frontend code automatically unless explicitly authorized. Document root causes and propose frontend-specific fixes.

## 8. Frontend Performance and Stability

Test:
- Continuous module navigation; rapid tab switching.
- Repeated modal open/close, searches, and filter changes.
- Pagination; long forms; large tables; long scrolling.
- Back/Forward; viewport changes; slow UI; rendering/loading/empty states.
- Unhandled JavaScript exceptions; React/hydration errors; freezes; suspicious memory growth.

Monitor console errors, pageerror events, failed resources, unexpected document navigations, long tasks where measurable, and duplicate UI-triggered requests.

Distinguish frontend defects from backend/network failures or undetermined causes.

## 10. Test Execution Strategy

Phase 1 - Frontend Discovery:
Analyze routes, visible/conditional features, menus/modules, interactive components, and build coverage matrix.

Phase 2 - Smoke Testing:
Login, dashboard, main navigation, critical workflows, logout.

Phase 3 - Full Frontend Functional Testing:
Forms, data tables, CRUD UI, modals, file UI, notifications, permissions-related UI.

Phase 4 - Continuous User Journey:
Run long sequential workflows within one context and verify no unexpected login prompts, reloads, resets, stale account data, broken navigation, or accumulated JavaScript errors.

Phase 5 - Responsive and Stability:
Desktop/tablet/mobile, Back/Forward, repeated interactions, UI performance and stability.

Phase 6 - Regression:
Re-execute failed frontend scenarios after fixes; capture before/after evidence where possible.
